1 · Executive summary

InferRSI is a CLI-first experiment harness for LLM/diffusion inference optimization, built around one unusual bet: the bottleneck in agent-driven optimization is not the agent — it is the absence of a trustworthy evidence contract. The repo packages three things into one Python package: (a) an AB/BA A/B experiment runner with source fingerprinting and quality gates, (b) a curated, source-cited knowledge base of tuning lessons exportable as context for coding agents (Codex, Claude, etc.), and (c) a first-class evidence/ tree where every performance claim must land as inspectable artifacts.

The most distinctive engineering choice is the verdict discipline: exactly three verdicts exist — PASS FAIL INCONCLUSIVE — and PASS requires pinned baseline/candidate SHAs, validators frozen before candidate search, and a complete evidence tree. Missing evidence is never rounded up to success; it stays INCONCLUSIVE. The README itself applies this to its own numbers: a locally adjudicated 30.60% latency reduction on 4×B300 is presented as a recorded PASS, while an imported Ascend NPU −22% result is explicitly labeled "not independently verified by this import."

3 · The core idea: optimize with evidence, reuse reviewed lessons

InferRSI positions itself as the workbench between a human/agent optimizer and a target inference engine. You bring the benchmark and quality-check commands; the workbench runs controlled comparisons and refuses to let narrative outrun artifacts. The loop has three promises:

Profile first

Ground each optimization in measured bottlenecks and source-cited tuning knowledge (searchable by repo, backend, tier, scenario).

Prove the gain

Repeated AB/BA-ordered A/B against the target engine with quality gates, git source fingerprints, and a generated HTML evidence report.

Keep the lessons

Search prior experience, including failed directions, and export revision-pinned context bundles for coding agents.

RSI contract (from AGENTS.md, enforced by review)

  • Freeze gates before search — checklist and validator/ locked in plan/ before any candidate experiment.
  • One plane per campaign step — each iteration changes exactly one declared SIAS plane: harness | model | infra.
  • Emit RunSpec snapshots — repo × revision × backend × device × model × scenario recorded per run.
  • Evaluator + evidence win — agent narrative is never a PASS; verdicts follow frozen gates and artifacts.
What it is explicitly not (v0.1.0): no automatic model-backed search, no automatic knowledge promotion, no RunSpec auto-population; knowledge retrieval is read-only; candidate storage is separately authorized. Process-cleanup behavior still needs platform-specific validation.

4 · Architecture: the SIAS boundary

The package is split into three planes — Scenario/Input via harness, model, and infra seams — so that new campaigns (new model, new repo, new hardware) plug into one shared AB/BA scheduler, process cleanup, and performance adjudication instead of forking them.

harness/

9 files · ~915 LOC
  • runner.py — the one AB/BA loop for every scenario/target/backend; owns evidence lifecycle
  • improvement.py — bounded offline improvement controller (INV/DOM proposals, budget, holdout)
  • skill_evaluation.py — Codex client wrapper + skill trial harness
  • evaluation.py — evidence gates → verdicts
  • reporting.py — portable HTML evidence report
  • scenarios/ — external-command & media scenarios
Owns: scheduling, deadlines, evidence, adjudication
Never owns: device specifics, request schemas, kernels

model/

8 files · ~1,133 LOC
  • protocols/image.py — image request dataclass
  • protocols/metrics.py — the metric contract: one finite, positive, dotted-key float
  • validators/image.py — PNG comparison with campaign-supplied gates (SSIM/PSNR)
  • validators/flare.py — NVIDIA flare local-inference SSE validator
  • anthropic_agent.py — bounded direct Anthropic agent, frozen cost reservations, schema-validated output
Owns: payloads, metric schemas, quality checks
Never owns: scheduling, workers, hardware

infra/

15 files · ~837 LOC
  • targets/git.py — repository identity: revision + tracked diff + untracked fingerprint
  • platforms/{cuda,mlx}.py — device discovery/qualification (nvidia-smi CSV, macOS sysctl)
  • processes.py — ownership/cleanup of commands & supervised servers (incl. Windows Job Objects)
  • executors/local.py — deadline-bounded argv execution; never interprets results
  • artifacts.py — deterministic digests, atomic JSON evidence writes
Owns: identity, devices, transport, processes
Never imports: model or harness (dependency floor)

Dependency rules (test-enforced)

  • Entrypoints → harness; scenarios → model + infra; model → infra utilities.
  • Infra never imports model or harness. No shared package imports a campaign from examples/.
  • tests/test_module_boundaries.py proves extension adapters reuse the real scheduler and process executor rather than re-implementing them.
  • Metric contract: exactly one finite positive float with a dotted key; 0.0, booleans, and non-finite values are metric errors, not gains.

The offline harness-improvement controller (MVP)

A second, deliberately narrow lane: a single-step offline controller above the Skill Eval comparator. It accepts at most one INV (invariant) and one DOM (domain) text-edit proposal, materializes them as immutable Git snapshots, probes with balanced AB/BA pairing against H0, applies a fixed lexicographic quality-then-known-tokens selection, mandates an independent successor rerun, and ends in exactly one held-out accept/reject gate that can never select a different candidate. Budget (call allowance, absolute deadline, observed-token threshold) carries across all stages; unknown token usage stops the loop and retains H0. It makes zero proposal-model calls and never promotes skills.

6 · The evidence contract

This is the heart of the repository. A public PASS requires all three of:

  1. Pinned revisions — baseline and candidate SHAs recorded in the acceptance issue (.github/ISSUE_TEMPLATE/campaign-acceptance.yml collects campaign_id, both SHAs, RunSpec, gates, evidence paths, verdict, downstream citation).
  2. Validators frozen before candidate search — validator/ + gate checklist locked in plan/.
  3. A complete evidence tree under evidence/<campaign-id>/:
evidence/<campaign-id>/ ├── plan/ hypothesis, RunSpec snapshot, frozen gate checklist ├── results/ metrics, logs, verdict rationale ├── patch/ candidate diff or revision pointer └── validator/ frozen validator definition + inputs
  • Verdict semantics: PASS pinned comparison + complete evidence + every gate met · FAIL complete evidence shows a missed gate · INCONCLUSIVE missing freeze, incomplete runs, unqualified environment.
  • Claim wording is standardized: "on candidate versus baseline, under this RunSpec, we observed …" linking the acceptance issue and revisions.
  • Model integrity = SHA-256 of actual file bytes; size/mtime equality is metadata only. A crashed or interrupted validator forces INCONCLUSIVE even if samples look fine.
  • Negative results are kept as scoped rejected-direction cases with revisit checks — a diagnostic option, not a blacklist.

Validation ladder L0–L4 (portable bars)

LevelFocusPortable bar
L0Operator correctness — numerical contracts, edge cases, fallbacksA PASS on latency / throughput / SLO wording requires L4 (or campaign-defined e2e) evidence in results/; L0–L2 cannot justify service claims. Numeric thresholds live in acceptance issues and frozen plan/ — never in CI, skills, or repo constants. Missing levels or env mismatch ⇒ INCONCLUSIVE.
L1Microbenchmark — fixed inputs, shapes, warmup policy, timing
L2Isolated scenario — stage behavior and integration
L3Model / modality quality — complete outputs under a frozen quality protocol
L4End-to-end service — full workload, latency/throughput/SLO, stability
Microbench ≠ service gain is stated as a hard rule, and the repo honors it: the H18 Triton launch-API probe measured host enqueue 6.41 → 3.95 µs but was recorded as "no E2E integration" — a probe, not a claim. The engine-delivery template repeats: "Do not infer E2E gain by multiplying kernel speedups."

11 · Governance, audit, and history

Acceptance-issue-first workflow

Work is issue-led: an acceptance issue (structured YAML form) must exist before a PASS is claimed; scoped-task issues bound non-performance work; the PR template separates "delivers / does-not-deliver," requires a checks-actually-run table, and forbids self-declared merge approval. DCO sign-off (git commit -s) is required.

Source audit: 34 review points

A user-supplied external review of main @ ac70272 was translated into 34 tracked follow-ups across six areas — correctness (P0s: server-helper platform contract, hostname leakage), evidence verification, shared contracts, engineering/public use (licensing of UNKNOWN imported licenses), performance/scalability, and architecture (authorized evidence-to-knowledge workflow). The audit doc is careful to note priorities are the reviewer's proposals, "not confirmed severity ratings," and that the delivery slice covered only four of the items — the rest remain open work, published transparently.

Velocity

The repository went from initialization (2026-10-07/08) to: a passing 30.60% B300 campaign with upstream PR, an imported NPU campaign, a 413-file FP8 search evidence tree (INCONCLUSIVE, kept), a 761-test suite, a 100-document skill library, and a six-workflow CI system — in 20 days, with 132 commits from 8 contributors. Historical context lives in PHASE1_REPORT.md (meta-skill bootstrap: performance-ceiling analysis with a 3-level roofline model; repository-evolution analysis of 3,428 commits; npu-skill-factory lifecycle) and SUBMISSION_NOTES.md (first-party skill packaging checklist).

Engine delivery template

docs/template/ is a copyable scaffold for delivering independent InferMatrixLab engines with scoped evidence and a recipe for the catalog — one recipe = one model × engine × backend × hardware × precision × task; deployment states unverified / validated / unsupported; "catalog registration is not a new hardware verification." Copying it creates no InferRSI runtime dependency.

12 · Assessment

Strengths

  • Claim hygiene as a product. The 3-verdict contract, frozen validators, pinned SHAs, and INCONCLUSIVE-by-default are enforced consistently from claim.py up to README wording — including against the authors' own results (a −29.81% miss retained as FAIL).
  • Small, auditable core. 6.5k LOC, zero runtime deps, stdlib-only; strict plane dependencies enforced by tests; the AB/BA loop exists exactly once.
  • Negative results are first-class. Rejected hypotheses, failed gates, and even CI rejection diagnostics are preserved with provenance — rare and valuable for an optimization project.
  • Real validation depth. Pixel-identity + SSIM/PSNR gates per channel, AB/BA ordering, warmup separation, seed discipline, source fingerprinting, frozen-bytes CI against Git mutation.
  • AI-labor governance. Model allow-lists, effort floors, encrypted rejection captures, and authorship declarations anticipate agent-heavy contribution flows.

Limitations & risks

  • Pre-release. v0.1.0 unpublished; no API stability; several headline capabilities (auto search, knowledge promotion, RunSpec auto-population) unimplemented.
  • No statistical significance. B300 headline uses medians of trial means; the docs say so, but n is small and the repo itself flags "significance not established."
  • Imported results asymmetry. The Ascend −22% and all external-engine tables rest on author reports; the repo labels them correctly, but readers must notice the labels.
  • 34 open audit items include P0s (platform contracts, artifact hostname leakage, licensing of UNKNOWN imports) — acknowledged, not yet closed.
  • Evidence tree weight. 6.9 MB / 556 files of committed evidence (plus Releases-hosted archives) is a deliberate trade: reproducibility over repo ergonomics.
  • Skill eval hasn't yet shown value: v2 found no skill improving correctness over baseline — an honest null result that questions the current skill packaging.
Analyst's note (opinion, not the repo's claim): InferRSI's moat is not the harness code — A/B runners are common — but the end-to-end discipline stack: verdict enum + frozen gates + evidence tree + negative-result retention + AI-authorship policy, all mutually reinforcing and cheap to audit.
